# معماری نهایی برای Free-plan — ۵۰۰۰ کاربر در روز

> این معماری طوری چیده شده که سایت بدون هیچ پلن پولی، تا حدود **۵۰۰۰ کاربر فعال در روز** دوام بیاورد. کلید کار، گذاشتن هر داده‌ای روی سرویسی است که **سقف رایگان آن برای نوع دسترسی ما** بزرگ‌تر است — نه صرفاً «کجای قدیمی بوده».

## خلاصه در یک نگاه

| لایه | چه داده‌هایی | چرا اینجا |
|---|---|---|
| **D1 اصلی** (اکانت سایت) | کاربران، کیف پول، تراکنش‌ها، آثار (فیلم/سریال)، نسخه‌ها، لینک‌ها، شمارنده‌های روزانه، rate-limit، توکن‌های موقت، آمار | ماندگار **و** پرتکرار نوشتن — سقف نوشتن رایگان D1 (۱۰۰ هزار/روز) تنها جایی است که این حجم نوشتن را می‌خورد |
| **KV** | فقط داده‌های کم‌تغییر و cache: `set` (تنظیمات)، `res:` (کش پست‌ها)، `gallery:`، `ads`، `catrev`، mirrorهای قدیمی | نوشتنشان روزی چند بار است؛ خواندن با `cacheTtl` لبه‌ای |
| **CACHE_KV** (اختیاری) | آمارهای دورusable جدا از KV اصلی | یک namespace جدا = یک سهم ۱۰۰هزارخوان/روز جدا |
| **Durable Object** (`EDITOR`) | صف‌های EDITOR، retry انتشار، mirrorها (`queue:`, `failed:`, `mirror-pair:`)، و پیام پایان انتظار محدودیت دانلود (`dln`) | از قبل این‌جا هستند — پایدار و بدون فشار روی KV/D1 |
| **Cache API** | صفحه HTML اصلی + `/api/catalog` (۶۰ ثانیه، کلیدشده با `catrev`) | خواندن‌های تکراری فهرست/صفحه را اصلاً به D1 نمی‌رساند |
| **Telegram (مخزن کانال)** | خود فایل‌های رسانه + مخازن پشتیبان mirror | فایل ۵۰۰ مگابایتی هرگز روی Cloudflare نمی‌آید |
| **فدراسیون D1 (اختیاری)** | فقط رکوردهای `it:`/`sub:` پخش‌شده بین دیتابیس‌های اکانت‌های دیگر | پخش حجم آثار بین چند D1 رایگان |

## چرا شمارنده‌ها و rate-limit روی D1 و نه KV؟

این مهم‌ترین تصمیم معماری است و با حدس زده نشده — از روی اعداد حد رایگان:

| سرویس (Free-plan) | خواندن/روز | نوشتن/روز |
|---|---|---|
| KV | ۱۰,۰۰۰ | **۱,۰۰۰** |
| D1 (رکورد) | ۵,۰۰,۰۰ | **۱۰۰,۰۰** |
| Workers (درخواست) | ۱۰۰,۰۰ | — |
| Durable Object (فراخوانی) | ۱۰۰,۰۰۰ | — |

هر دانلود = نوشتن ۱ شمارنده `dlc:` + نوشتن ۱ rate-limit `rl:` + نوشتن ۱ `views:` + نوشتن ۱–۲ آمار تبلیغ `adstat:`. با ۵۰۰ کاربر و ~۱۰ هزار دانلود/روز، **تنها نوشتن‌های شمارنده/آمار ≈ ۴۰–۵۰ هزار/روز است** — یعنی ۵۰ برابر سقف نوشتن رایگان KV. اگر این‌ها روی KV بمانند، سایت از روز اول خطا می‌دهد. D1 با ۱۰۰ هزار نوشت/روز این‌ها را با حاشیه کافی می‌خورد، در حالی که خواندن‌های ما (≈ ۱۵۰ هزار رکورد/روز) از ۵ میلیون خیلی دور است.

بندهای «سنگین» (D1) فعلی:

```
u: it: src: sub: code: pay: refcode: tg: tgu: ph: k2k:
dlc: bot: rl: views: stars: tick: adstat:
dl: adg: tgstate: stm:                        + کلید دقیق idx
```

`dl:` (بلیت هر دانلود)، `adg:` (دروازهٔ تبلیغ هر دانلود)، `tgstate:` (حالت ورود) و `stm:` (جلسهٔ پخش آنلاین) در نسخهٔ 3.60 به D1 منتقل شدند. این‌ها **به ازای هر دانلود/ورود/پخش** نوشته می‌شوند. روی KV با سقف ۱۰۰۰ نوشتن روزانه، سهمیه بعد از چند صد دانلود تمام می‌شد.

بقیه (`set`, `res:`, `gallery:`, `ads`, `catrev`, `mirror:*` و…) روی KV می‌مانند.

## بودجهٔ ۵۰۰۰ کاربر/روز (برآورد محافظه‌کارانه)

فرض: ۵۰۰۰ کاربر × ۶ درخواست = **۳۰,۰۰۰ درخواست/روز** (سقف Workers: ۱۰۰,۰۰۰ ✅)

| سرویس | مصرف برآوردی | سقف رایگان | وضعیت |
|---|---|---|---|
| Workers requests | ۳۰k | ۱۰۰k | ✅ |
| D1 row reads | ~۱۵۰k (بخش قابل توجهی‌اش با Cache API حذف می‌شود) | ۵M | ✅ |
| D1 row writes | ~۷۰k (شمارنده‌ها + rate-limit + views + آمار + کاربران/آثار) | ۱۰۰k | ⚠️ در ریزش‌های سنگین نزدیک می‌شود؛ فدراسیون یا کاهش آمار تبلیغ فاصله می‌دهد |
| KV reads | ~۲۰k (تنظیمات با cacheTtl ۳۰ ثانیه + res: + …) | ۱۰k | ✅ |
| KV writes | < ۲۰۰ (تنظیمات/تبلیغات/کش پست‌ها) | ۱,۰۰۰ | ✅ |
| DO invocations | < ۵k | ۱۰k | ✅ |
| Cache API | آزاد (باندوِرد Workers) | — | ✅ |

اگر روزها داغ‌تر از برآورد شد، اولویت‌های رشد به این ترتیب هستند:
1. **فدراسیون D1** — آثار را بین اکانت‌ها تقسیم کنید (هر شارد = +۵M خوان / +۱۰۰k نوشت رایگان). راهنما: [D1-SHARDS.md](D1-SHARDS.md).
2. **CACHE_KV جدا** — اگر هنوز ندارید بسازید؛ آمار دورusable از سهم KV اصلی خارج می‌شود.
3. **کاهش نوشتن آمار تبلیغ** — `adstat:` را دورusable کنید یا نمایش تبلیغ را برای کاربران فعال کمتر کنید.
4. پلن پولی Workers (هر ۵۰۰ درخواست ۵ دلار) معمولاً آخرین و آسان‌ترین گزینه است.

## پخش آنلاین و تبلیغات خودکار (نسخهٔ 3.60)

| بخش | کجا اجرا می‌شود | هزینه برای سهمیهٔ سایت |
|---|---|---|
| پلیر | فایل جدای `/assets/player.js` با کش immutable | عملاً یک‌بار برای هر کاربر |
| شروع/تعویض/تمدید پخش | `POST /api/stream/open` (+ `/stream/src` بعد از تبلیغ) | ۱ تا ۳ درخواست و **۱ نوشتن D1** (`stm:`) برای هر جلسه |
| بایت‌های ویدئو | **لبه‌های پخش** روی اکانت‌های دیگر (`scripts/stream-edge-worker.js`)؛ بدون لبه، همین Worker زیر `/sv` | با لبه: صفر. بدون لبه: ~۳–۲۰ درخواست برای هر تماشای MP4. HLS هر قطعه یک درخواست است. |
| انتخاب تبلیغ | داخل خود سایت از روی فهرست کش‌شدهٔ پلتفرم (هر ~۹۰ ثانیه) | صفر نوشتن |
| رویدادهای تبلیغ | تجمیع در حافظه و ارسال دسته‌ای هر ~۲۰ ثانیه به `ads.js` | صفر نوشتن روی D1 سایت؛ نوشتن‌ها روی اکانت پلتفرم است |
| نمایش بنرهای پلیر | `navigator.sendBeacon` دسته‌ای به `/api/ad/evs` | یک درخواست برای چند بنر |
| پلتفرم تبلیغ‌دهندگان | Worker و D1/KV جدا روی اکانت دیگر (`ads.js`) | صفر |

برآورد اضافهٔ ۵۰۰۰ کاربر روزانه با ۲۰۰۰ جلسهٔ پخش و لبهٔ جدا: حدود **۴ تا ۶ هزار درخواست** و **۲ تا ۳ هزار نوشتن D1** روی اکانت سایت. جزئیات: [ONLINE-PLAYER.md](ONLINE-PLAYER.md) و [ADS-PLATFORM.md](ADS-PLATFORM.md).

## حالت‌های STORAGE_BACKEND

| مقدار | رفتار |
|---|---|
| `kv` (پیش‌فرض) | همه‌چیز روی KV — حالت قدیم، بدون D1. اگر D1 binding هم وصل باشد، باز هم همه KV. |
| `hybrid` (توصیه‌شده) | سنگین‌ها روی D1، بقیه KV. **اگر D1 هنوز migrate نشده باشد، سنگین‌ها خودکار به KV تنزل می‌کنند** و سایت نمی‌ریزد. |
| `d1` (قدیمی) | همه‌چیز روی D1 (مسیر قبل) — برای سازگاری نگه داشته شد. |

انتقال از KV به D1 با همان ابزار قبلی `/storage-migration` انجام می‌شود؛ فقط در انتها به‌جای `d1` مقدار `hybrid` را بگذارید.

## مسیر یک دانلود در معماری جدید

```
درخواست کاربر
  → Cache API: صفحه/فهرست؟ (HIT → تمام)
  → توکن: tick:/u: از D1 (cacheTtl لبه‌ای ۳۰ ثانیه)
  → اثر: it: از D1 — یا از شارد فدره‌شده (hash کلید)
  → محدودیت دانلودِ پشت‌سرهم: dlc:st:<کاربر> (+ سقف کل روزانهٔ ربات dlc:bot: اگر روشن باشد) + rl: روی D1
  → ارسال فایل: Telegram Bot API + مخزن کانال (+ fallback به mirrorهای DO)
  → نوشتن آمار: views:/adstat:/dlc: روی D1
```

## فهرست کلیدها

| کلید/پیشوند | محل | ماهیت |
|---|---|---|
| `u:` `tg:` `tgu:` `ph:` `refcode:` | D1 | کاربران و نقشه‌های هویتی |
| `it:` `src:` `sub:` `idx` | D1 / شارد | آثار، منابع، زیرنویس، فهرست |
| `code:` `pay:` `k2k:` `stars:` | D1 | کدها، فاکتورها، تراکنش‌ها |
| `dlc:` `bot:` `rl:` `views:` `adstat:` `tick:` | D1 | شمارنده‌ها، rate-limit، آمار، توکن موقت |
| `dl:` `adg:` `tgstate:` | D1 | بلیت دانلود (۱۰ دقیقه)، دروازهٔ تبلیغ دانلود (۳۰ دقیقه)، حالت ورود ربات |
| `stm:<username>` | D1 | جلسه‌های پخش آنلاین هر کاربر (`{list:[{sid,at}]}`، TTL یک روز) برای سقف پخش هم‌زمان |
| `dlc:st:<username>` | CACHE_KV اگر بسته شده باشد، وگرنه مثل بقیهٔ `dlc:` (D1/KV) | وضعیت «محدودیت دانلودِ پشت‌سرهم» هر کاربر: `{n, lvl, until, last, nfy, v}`. هر دانلود ۱ نوشتن (همان‌قدر که شمارندهٔ روزانهٔ قبلی)؛ TTL خودکار = پایان انتظار + زمان بازنشانی (۲ دقیقه تا ۴۸ ساعت) |
| `set` | KV | تنظیمات سایت (کم‌تغییر، cacheTtl ۳۰s) |
| `res:` | KV | کش پست‌های تلگرام (TTL ۹۰ دقیقه) |
| `gallery:` `ads` | KV | پوسترهای گالری و آرایه تبلیغات |
| `catrev` | KV | نسخهٔ محتوا برای بی‌اعتبارسازی Cache API |
| `mirror:*` `mirror-pair:` `mirror-active:` | KV (قدیمی) + DO | نگاشت mirrorها |
| `queue:` `failed:` (داخل DO) | Durable Object | صف‌های انتشار و retry |
| `dln` (نمونهٔ DO با نام `dln:<tgId>`) | Durable Object | پیام «محدودیت دانلود برداشته شد»: فقط برای کاربری که به محدودیت خورده، یک رکورد + یک alarm (بدون cron). بعد از ارسال پاک می‌شود؛ بدون بایندینگ `EDITOR` فقط ارسال پیام انجام نمی‌شود |
