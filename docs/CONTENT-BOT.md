# ربات سوم مدیریت محتوا — یکپارچه در worker.js

## قابلیت این نسخه

این ربات در همان فایل جاوااسکریپت `worker.js` و همان Worker سایت اجرا می‌شود و برای **اثر موجود در سایت** است. مدیر لینک صفحه اثر را می‌فرستد، ربات عنوان/سال/خلاصه را از همان سایت می‌خواند و سپس چهار دسته فایل را دریافت می‌کند: دوبله، هاردساب، سافت‌ساب و زبان اصلی. هر دسته با `/next` قابل ردکردن است. فایل‌ها ابتدا پیش‌نویس هستند و فقط پس از `/review` و `/confirm` منتشر می‌شوند.

- مثال نام قابل تشخیص: `Silo.S02E03.1080p.mkv` یا `Silo.2x03.720p.mkv`.
- کیفیت‌های 480، 720، 1080 و 2160/4K؛ فصل و قسمت از نام فایل، نه حدس ثابت فصل ۱.
- نام نامشخص/نام متفاوت، چندقسمتی بودن فایل یا نبود کیفیت، به تعیین تکلیف مدیر نیاز دارد.
- نام اثر انتخاب‌شده ملاک مقصد است. ربات خودسرانه اثر جدیدی نمی‌سازد و نام فایل به‌تنهایی مجوز تغییر مقصد نیست.
- امکان ارسال فایل، فوروارد فایل از کانال یا لینک `https://t.me/c/.../...`. لینک تنها، نام فایل ندارد و معمولاً به `/assign` نیاز دارد.
- عنوان نسخه را در کپشن فایل بنویسید. نوع دوبله/زیرنویس از مرحله فعلی مشخص می‌شود، نه از حدس نام فایل.
- هر پیش‌نویس حداکثر ۲۰ فایل؛ بعد از ثبت، لینک همان اثر را دوباره بفرستید و دسته بعدی را اضافه کنید.
- فایل‌ها با `copyMessage` در مخزن فعلی کپی می‌شوند؛ Worker فایل‌های چندگیگابایتی را دانلود نمی‌کند و `file_id` یک ربات را به ربات دیگر نمی‌دهد.
- فایل‌های منتشرشده توسط ربات ارسال فعلی سایت از آدرس پیام مخزن دریافت می‌شوند.
- برای پیش‌نویس‌ها از یک Durable Object برای هر مدیر استفاده می‌شود، نه ساخت رکورد جدید KV برای هر پیام گفتگو. یک هماهنگ‌کننده انتشار درخواست‌های ربات را ترتیبی انجام می‌دهد.

## دو مسیر مستقل ورود محتوا

- **گفتگوی خصوصی:** روند مرحله‌ای، پیش‌نمایش و تأیید نهایی بالا همچنان فعال است.
- **کانال منبع:** با `CONTENT_CHANNEL_RULES` و سربرگ مشخص، پست‌های جدید مستقیماً و خودکار منتشر می‌شوند. نام نسخه/نوع از متن قبل از فایل و فصل/قسمت/کیفیت از نام فایل استخراج می‌شود. راهنمای کامل و نمونه الگو در [CHANNEL-AUTOMATION.md](CHANNEL-AUTOMATION.md) است.

برای جلوگیری از ثبت دوگانه، مسیر قدیمی واردسازی برای مخزن فعلی و کانال‌های منبع و مقصد مشخص‌شده در `CONTENT_CHANNEL_RULES` غیرفعال می‌شود؛ سایر کانال‌ها رفتار قبلی را دارند. هویت ربات‌های ورود/ارسال تغییر نمی‌کند.

ربات فقط پست‌های جدیدی را می‌بیند که تلگرام پس از فعال‌شدن webhook تحویل می‌دهد؛ خواندن آزاد تاریخچه یا پیوستن خودکار به کانال خصوصی با Bot API انجام نمی‌شود. انتقال خودکار پست‌های جدید به حداکثر سه مقصد پشتیبانی می‌شود؛ فایل‌های آلبوم به صورت پیام‌های جدا منتقل می‌شوند.

## استقرار یک Worker، یک فایل JavaScript

فقط **`worker.js`** فایل اجرایی سایت، وبهوک ربات مدیریت، منطق گفتگو و کلاس `EditorSession` است. فایل ربات مستقل حذف شده و هیچ Service Binding به Worker دوم لازم نیست. پسوند `.mjs` قبلی هم JavaScript بود؛ اکنون فایل اجرایی همان `.js` سایت است.

### ۱. تنظیمات روی Worker فعلی سایت

ربات سوم را در BotFather بسازید؛ هویت آن در تلگرام همچنان جدا از ربات ورود و ربات ارسال است، اما کد هر سه روی همین Worker اجرا می‌شود.

در **Settings → Variables and Secrets** همین Worker:

- Secret: `CONTENT_BOT_TOKEN` — توکن ربات سوم، متفاوت از توکن ورود و ارسال.
- Secret: `CONTENT_WEBHOOK_SECRET` — مقدار تصادفی ۳۲ تا ۲۵۶ کاراکتر از حروف/عدد/خط‌تیره/آندرلاین.
- Variable: `CONTENT_ADMIN_IDS` — شناسه عددی تلگرام مدیران، جداشده با ویرگول.
- Variable اختیاری: `SITE_PUBLIC_ORIGIN` — دامنه HTTPS سایت، بدون مسیر. اگر نباشد از `publicUrl` در تنظیمات سایت استفاده می‌شود.

مدیر باید **هم در فهرست شناسه‌ها باشد و هم نقش admin در حساب سایت داشته باشد**. توکن‌ها را در کد، Git یا چت وارد نکنید. `CONTENT_BOT_SECRET` و binding قبلی `SITE` دیگر استفاده نمی‌شوند؛ مسیر HTTP قدیمی `/api/content-bot/*` هم بسته شده است. ارتباط ربات و سایت یک فراخوانی داخلی تابع است، نه درخواست شبکه به خود Worker.

### ۲. Bindingها و migration

- `KV`: دقیقاً همان namespace فعلی سایت؛ دیتابیس تازه و خالی نسازید.
- `EDITOR`: یک Durable Object با کلاس `EditorSession` **در همین Worker**.
- migration کلاس SQLite باید ثبت شود. `wrangler.example.toml` نمونه تنظیمات است؛ نام Worker و شناسه namespace را با مقادیر واقعی فعلی جایگزین و سایر bindingها/متغیرهای موجود را حفظ کنید.

**صرفاً Paste کردن کد، Durable Object را ایجاد نمی‌کند.** برای ثبت کلاس و migration از Wrangler استفاده کنید. این یک منبع ذخیره‌سازی گفتگو است، نه یک Worker/سایت دوم. هر فایل پیش‌نویس در KV رکورد گفتگو جداگانه نمی‌سازد. سهمیه و هزینه Durable Objects جدا از KV را بررسی کنید.

اگر قبلاً تنظیمات Wrangler دارید، فقط binding و migration جدید را به همان تنظیمات اضافه کنید؛ تاریخچه migrations قبلی را حذف نکنید. نمونه مخزن را بدون جایگزینی مقادیر و حفظ تنظیمات فعلی روی سرویس واقعی deploy نکنید.

```sh
# پس از آماده‌کردن wrangler.toml واقعی و حفظ KV/bindingهای قبلی:
npx wrangler deploy
```

Secrets را از پنل کلودفلر یا `wrangler secret put` روی **همین Worker** تنظیم کنید. ربات سوم و ربات ارسال فعلی باید مدیر مخزن باشند. برای حذف پیش‌نویس، ربات سوم به مجوز حذف پیام نیاز دارد. تنظیمات مخزن فعلی سایت باید صحیح باشد.

### ۳. ثبت وبهوک از پنل خود سایت

پس از انتشار و تکمیل تنظیمات، در **پنل ادمین ← تنظیمات ← ربات مدیریت محتوا — یکپارچه با سایت** روی **ثبت وبهوک ربات مدیریت** بزنید.

مسیر وبهوک:

```text
https://YOUR-SITE/api/tg/content-webhook
```

این دکمه webhook ربات سوم را برای پیام خصوصی و `channel_post` تنظیم می‌کند، پیام‌های معوق را حذف نمی‌کند و از تنظیم توکن مشابه ربات ورود/ارسال جلوگیری می‌کند. دیگر به اسکریپت محلی جدا برای ثبت وبهوک نیاز نیست. در صورت خطا، پنل وضعیت را نمایش می‌دهد بدون نمایش توکن.

### انتقال از نسخه مستقل قبلی

اگر ربات مستقل را واقعاً مستقر کرده‌اید، **ابتدا تمام پیش‌نویس‌های آن را ثبت یا لغو کنید**؛ گفتگوهای Durable Object در Worker قدیمی خودکار به Worker سایت منتقل نمی‌شوند. سپس نسخه یکپارچه را مستقر و webhook را با دکمه پنل به مسیر جدید منتقل کنید. بعد از اطمینان از عملکرد و نبود پیش‌نویس فعال، می‌توانید Worker مستقل و Service Binding/secret مشترک قدیمی را کنار بگذارید. migration قبلی را حذف نکنید و نشست قدیمی با انتشار نامشخص را بدون بررسی پاک نکنید.

## نمونه گفتگو

```text
https://YOUR-SITE/#/item/i_123abc
[فایل Silo.S02E03.1080p.mkv با کپشن «نسخه بدون سانسور»]
/next
[فایل‌های هاردساب]
/next
[فایل‌های سافت‌ساب]
/review
/confirm
```

فرمان‌های دیگر:

- `/assign 2 3 1080`: اصلاح فایل منتظر به فصل ۲ قسمت ۳ کیفیت 1080؛ برای فیلم `/assign 1 1 1080`.
- `/accept`: تأیید مقصد فایل با نام مبهم، فقط اگر کیفیت و فصل/قسمت معتبر باشند.
- `/skip`: کنارگذاشتن فایل منتظر.
- `/remove 2`: حذف فایل دوم پیش‌نویس از مخزن و پیش‌نویس.
- `/refresh`: دریافت مجدد اطلاعات اثر پس از ویرایش در سایت، سپس بررسی مجدد و تأیید.
- `/cancel`: حذف فایل‌های پیش‌نویس از مخزن و پایان گفتگو.

پیش‌نویس غیرفعال پس از ۲۴ ساعت لغو و فایل‌های آن پاک می‌شود؛ حذف پیام منوط به محدودیت‌های تلگرام و مجوز ربات است. تا وقتی نتیجه انتشار نامعلوم است، حذف/لغو و انقضا متوقف می‌شود تا فایل احتمالاً منتشرشده پاک نشود. در این حالت `/confirm` برای ادامه همان انتشار است؛ پس از لغو دسترسی مدیر ممکن است بررسی دستی لازم شود.

## ایمنی و محدودیت‌ها

- همه فایل‌ها قبل از نوشتن اثر اعتبارسنجی می‌شوند؛ نوع و کیفیت پیش‌فرض نامعلوم نداریم.
- مراحل حذف/ردکردن را با محتوای آزمایشی تست کنید. از پایگاه داده پشتیبان بگیرید.
- درج فایل‌ها شناسه ثابت دارد و رسید انتشار داخل همان رکورد اثر نگهداری می‌شود (آخرین ۱۶ رسید). retry معمولی پس از خطای شبکه نسخه اضافه تکراری نمی‌سازد و ایندکس‌های ناقص را ترمیم می‌کند.
- پیام‌های تکراری webhook در هر نشست با شناسه update کنترل می‌شوند. با این حال API تلگرام و ذخیره Durable Object تراکنش مشترک ندارند؛ قطع ناگهانی دقیقاً پس از کپی و قبل از ثبت نتیجه ممکن است پیام اضافی در مخزن باقی بگذارد. تضمین exactly-once ارائه نمی‌شود.
- انتشارهای ربات ترتیبی‌اند و تغییر نسخه اثر بررسی می‌شود، اما KV تراکنش/CAS ندارد: همزمان با تأیید ربات، همان اثر را در پنل یا مسیرهای دیگر ویرایش نکنید. شمارنده‌ها یا سایر مدیران روی KV همچنان محدودیت سازگاری نهایی دارند.
- تشخیص واقعی صوت یا وجود subtitle با تحلیل محتوای ویدئو انجام نمی‌شود؛ انتخاب مدیر ملاک است.
- رمزها، شماره‌ها، کلید امضای نشست و فایل‌های کامل کاربران وارد لاگ یا Git نشوند.

## تست

```sh
node tests/check.mjs
node tests/content-bot.mjs
node tests/channel-automation.mjs
node --input-type=module --check < worker.js
```

تست‌های محلی روی همان ماژول `worker.js` با تلگرام و KV ساختگی اجرا می‌شوند؛ بسته‌بودن API ارتباطی قدیمی، محافظت وبهوک، ثبت وبهوک از تنظیمات و عملکرد سایت بدون فعال‌کردن ربات هم بررسی می‌شود.  صحت مجوز کانال و ارسال/حذف واقعی تلگرام باید در استقرار آزمایشی بررسی شود. هیچ webhook یا namespace واقعی توسط این تغییرات محلی تنظیم نشده است.
