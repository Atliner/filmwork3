# فدراسیون D1 — چند دیتابیس روی اکانت‌های متفاوت، یک سایت

> هدف: وقتی حجم آثار (فیلم/سریال) زیاد شد، رکوردهای `it:`/`sub:` را بین چند D1 روی **اکانت‌های متفاوت Cloudflare** تقسیم کنیم تا سقف رایگان هر اکانت دیرتر تمام شود — بدون تغییر آدرس سایت و بدون جابه‌جایی داده‌های کاربری.

## اصل کار

```
سایت اصلی (اکانت ۱)
  D1 اصلی ← کاربران، کیف پول، تراکنش‌ها، idx، src:  (هرگز نمی‌روند بیرون)
     │
     │  hash قطعی کلید (FNV-1a) ÷ تعداد شارد
     ├──→ شارد A (اکانت ۲) ← فقط it:… / sub:… با hash صفر
     └──→ شارد B (اکانت ۳) ← فقط it:… / sub:… با hash یک
```

- **مسیریابی قطعی:** کلید `it:abc` همیشه به همان شارد می‌رود (hash کلید)، پس هیچ ادغام/تطبیق فهرست (merge/dedupe) لازم نیست.
- **فهرست عمومی (`idx`) باقی‌ماندهٔ محلی:** فهرست سایت یک کلید کوچک (~۵۰۰ سطر) در D1 اصلی است و از شارد‌ها خوانده نمی‌شود.
- **تنزل خودکار:** اگر شارد قطع شود، خواندن از D1 اصلی ادامه می‌شود (نسخه‌های قدیمی آثار) و نوشتن‌ها در D1 اصلی جمع می‌شوند تا شارد برگردد؛ سایت هرگز ۵۰۳ نمی‌دهد.
- **حذف اثر** همزمان از شارد و D1 اصلی انجام می‌شود.

## نصب یک شارد (۵ دقیقه)

1. **روی اکانت دیگر** (اکانت ۲، ۳، …) نصب‌کننده را اجرا کنید — فقط Worker جدید می‌سازد و هیچ Worker موجودی را دست نمی‌زند:

   ```
   node scripts/shard-installer.mjs
   ```

   نصب‌کننده ورود مرورگری Cloudflare می‌گیرد، Worker را با D1 مقصد + یک `SHARD_SECRET` تصادفی می‌سازد و **آدرس + رمز** را چاپ می‌کند.
   (می‌توانید دستی هم بزنید: Worker جدید + فایل `scripts/shard-proxy-worker.js` + binding D1 با نام `SHARD_DB` + Secret `SHARD_SECRET`.)

2. **در پنل سایت:** `تنظیمات ← ذخیره‌سازی و فدراسیون D1`
   - شناسه (مثلاً `d1-2`)، آدرس shard-proxy و رمز را وارد کنید.
   - دکمه «🧪 تست اتصال» → «افزودن».

3. تمام. آثار جدید از همین لحظه بین شارد‌ها تقسیم می‌شوند. هر شارد تا ۸ مورد مجاز است.

## امنیت شارد

- هر درخواست شارد با **HMAC-SHA256** روی `method + path + hash(body) + زمان + nonce` امضا شده است؛ پنجره زمانی ±۵ دقیقه و nonce تکراری رد می‌شود.
- رمز (SHARD_SECRET) در هر دو سمت پیش از امضا از فاصله/Enterهای انتهایی پاک می‌شود؛ اگر Secret را با paste ساخته‌اید و Enter انتهایی داشت، باز هم کار می‌کند.
- شارد **فقط** کلیدهای `it:`/`sub:` را می‌پذیرد؛ حتی با داشتن رمز، کاربر/کیف پول/تراکنشی قابل خواندن نیست.
- رمز در تنظیمات سایت (داخل KV/D1) ذخیره می‌شود و در پاسخ‌های پنل نمایش داده نمی‌شود.
- ترافیک شارد = تعداد خواندن/نوشتن آثار فقط؛ با ۵۰۰ کاربر/روز، هر شارد روزی چند‌هزار درخواست می‌شود — بسیار پایین‌تر از ۱۰۰ هزار درخواست رایگان هر اکانت.

## عیب‌یابی سریع

| پیام تست اتصال | دلیل | راه‌حل |
|---|---|---|
| **امضا تأیید نشد (bad-signature)** | نسخهٔ قدیمیِ `shard-proxy-worker.js` مستقر است (باگ تبدیل امضا به hex — همهٔ درخواست‌ها رد می‌شد) یا رمز دو طرف فرق می‌کند | فایل **به‌روز** `scripts/shard-proxy-worker.js` را دوباره Deploy کنید؛ معمولاً همان رمز قبلی کافی است. اگر نشد، Secret را روی شارد دوباره وارد کنید (بدون Enter انتهایی) و در پنل سایت همان را بگذارید. |
| **روی شارد، Secret به اسم SHARD_SECRET تنظیم نشده** | Secret اشتباه ساخته شده (مثلاً با اسم دیگر) | در شارد، Secret با نام دقیق `SHARD_SECRET` بسازید. |
| **نسخهٔ Deployشدهٔ شارد قدیمی یا ناسازگار** | هدرهای امضا نمی‌رسند | کد جدید `shard-proxy-worker.js` را Deploy کنید. |
| **دیتابیس D1 با نام SHARD_DB متصل نشده** | Binding درست نیست | در بخش Settings → Bindings یک D1 با نام دقیق `SHARD_DB` وصل کنید. |
| **آدرس شارد درست نیست یا Worker پاسخ نمی‌دهد** | آدرس اشتباه/Worker غیرفعال | آدرس کامل `https://…workers.dev` را بدون اسلش انتهایی وارد کنید. |

نکته: `/health` شارد از نسخهٔ جدید `v: 2` را هم برمی‌گرداند تا سایت بتواند نسخهٔ کهنه را تشخیص دهد.

## مدیریت و عیب‌یابی

- **نمای وضعیت:** در همان باکس، برای هر شارد: ✓ سالم/✗ قطع، تاخیر (ms)، تعداد رکورد زنده (از `/health`) و در صورت ناسازگاری یک یادداشت («نسخهٔ شارد قدیمی است»). این وضعیت **واقعی** است: هر بار باز شدن پنل (و دکمهٔ «به‌روزرسانی وضعیت») یک `/health` امضاشده به هر شارد می‌زند و تا آمدن پاسخ، ردیف «… در حال بررسی» نشان داده می‌شود — قبلاً شاردی که تازه اضافه می‌شد همیشه «قطع» دیده می‌شد، چون هیچ بررسی‌ای انجام نمی‌شد.
- **افزودن با بررسی اتصال:** پیش از ذخیره، شارد با یک `/health` واقعی آزمایش می‌شود؛ اگر پاسخ نداد، ذخیره نمی‌شود و دلیلش نشان داده می‌شود (برای ذخیرهٔ اجباری، درخواست API با `force: true`). دلیل رد شدن هم دقیق است: امضای نامعتبر، تایم‌اوت، خطای شبکه یا `no-d1-binding`.
- **حذف شارد:** رکوردهای روی D1 آن شارد حذف **نمی‌شوند**؛ فقط از مسیریابی خارج می‌شوند. آثار روی آن تا جابه‌جایی دستی، از نسخهٔ D1 اصلی خوانده می‌شوند.
- **تغییر تعداد شارد، جابه‌جایی آثار را به‌هم نمی‌زند:** آثار قدیمی در شارد قبلی‌شان می‌مانند و با fallback محلی همیشه خوانده می‌شوند؛ فقط آثار جدید به جدول hash جدید می‌روند. اگر بخواهید آثار قدیمی را هم تقسیم کنید، باید از پنل حذف/دوباره ثبت کنید (توصیه: فقط وقتی شاردی را برای همیشه حذف می‌کنید).
- **پشتیبان شارد:** همان پشتیبان D1 اکانت آن شارد (در اکانت خودش). فایل‌های رسانه هم مثل قبل در تلگرام هستند.

## چرا «کاربران» هرگز فدره نمی‌شوند؟

کیف پول، تراکنش‌ها و هویت کاربران باید در یک نقطهٔ اتمیک واحد باشد (یک کاربر، یک مانده، در هر لحظه). این داده‌ها همچنین کوچک‌اند (۵۰ کاربر ≈ چند مگابایت)؛ فشار اصلی Free-plan از **آثار** است که قابل تقسیم‌اند. فدراسیون دقیقاً همین قسمت قابل تقسیم را هدف گرفته است.

## سؤالات پرتکرار

**س: می‌شود شارد روی اکانت خودم (همان اکانت سایت) باشد؟**
ج: بله — هر Worker با یک D1. ولی هدف اکانت‌های متفاوت است تا سهم ۵M خوان/روز **جدا** داشته باشند.

**س: اگر رمز شارد نشت کند چه؟**
ج: آن شارد را از پنل حذف کنید و روی اکانت شارد یک `SHARD_SECRET` جدید بسازید؛ رمز جدید را وارد کنید. داده‌ها باقی می‌مانند.

**س: فدراسیون داده‌ها را کپی می‌کند؟**
ج: نه. هر رکورد یک خانه دارد. نسخهٔ قدیمی روی D1 اصلی فقط به‌عنوان نسخهٔ پشتیبان خواندنی باقی می‌ماند (معمولاً همان رکورد اصلی همان اثر است؛ وقتی اثر جدید روی شارد نوشته می‌شود، نسخهٔ محلی فقط تا حذف اثر قدیمی‌تر می‌ماند).
