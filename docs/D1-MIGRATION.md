# انتقال سایت از KV به D1 — راهنمای مرحله‌ای

این تغییر **لایه ذخیره‌سازی سازگار با داده‌های فعلی** را به D1 اضافه می‌کند. اطلاعات آثار، نسخه‌ها، کاربران، کیف پول، رسیدها و تنظیمات با همان ساختار JSON فعلی داخل جدول `filmwork_records` نگهداری می‌شود؛ کلید اصلی و زمان انقضا ایندکس دارند. فایل‌های ویدئویی به دیتابیس منتقل نمی‌شوند.

این مرحله بازطراحی کامل جدول‌های فیلم/کاربر یا تراکنشی‌کردن تمام عملیات مالی نیست. منطق فعلی سایت و کنترل‌های تکرار عملیات حفظ شده‌اند. مهاجرت مرحله‌ای، همراه با checkpoint، از batch اتمیک D1 استفاده می‌کند. بازطراحی جست‌وجو، داده‌های بسیار بزرگ و عملیات مالی همزمان مرحله جداگانه‌ای است.

## پیش‌نیاز

- کد جدید روی **همان Worker فعلی** منتشر شده باشد.
- اتصال `KV` فعلی و `EDITOR` فعلی را نگه دارید؛ نام Worker و Secrets را عوض نکنید.
- پیش از حالت نگهداری، در سایت با حساب مدیر وارد شوید. این صفحه از نشست همان مرورگر استفاده می‌کند؛ توکن را جایی کپی نکنید.
- از ابزارهای دیگر روی همان KV استقرار/ویرایش انجام ندهید. تا پایان انتقال، KV باید ثابت بماند.

## ۱. ساخت دیتابیس — بدون SQL دستی

در داشبورد Cloudflare:

1. **Storage & databases → D1 SQL Database → Create database** را باز کنید.
2. یک دیتابیس خالی بسازید؛ نام پیشنهادی: `filmwork-main`.
3. به **Workers & Pages → Worker سایت → Bindings → Add binding → D1 database** بروید.
4. نام binding را دقیقاً **`DB`** بگذارید و دیتابیس ساخته‌شده را انتخاب کنید.
5. تغییرات را Deploy کنید. فعلاً سایت هنوز از KV استفاده می‌کند.

صرف اتصال DB، دیتابیس فعال سایت را تغییر نمی‌دهد. جدول‌ها را ابزار انتقال می‌سازد؛ اجرای دستی `migrations/0001-storage.sql` اختیاری است. رکورد ready را دستی در SQL وارد نکنید.

## ۲. ورود به حالت نگهداری

پیش از این مرحله مدیر باید وارد سایت شده باشد. در Variables همین Worker این دو متغیر متنی را تنظیم و **با هم** Deploy کنید:

```text
STORAGE_BACKEND = kv
STORAGE_MAINTENANCE = 1
```

سایت و webhookها موقتاً پاسخ 503 می‌دهند. ربات‌ها را از کانال حذف نکنید و صف Telegram را پاک نکنید. Telegram معمولاً webhook ناموفق را دوباره تلاش می‌کند، اما نگهداری طولانی می‌تواند از پنجره نگهداری رویدادهای آن عبور کند؛ انتقال را در زمان کم‌ترافیک انجام دهید.

حالت نگهداری تغییرات برنامه و alarmها را متوقف می‌کند؛ درخواست‌های قدیمی که **قبل از Deploy** شروع شده‌اند و ابزارهای خارجی را به‌صورت جادویی متوقف نمی‌کند. پیش از شروع، از پایان درخواست‌ها/استقرارهای قبلی و توقف تمام نویسنده‌های دیگر اطمینان پیدا کنید. برای انتشار تغییرات قبلی KV هم فرصت کافی بدهید؛ KV سازگاری فوری ندارد. انتقال را در زمان فعالیت مدیران دیگر یا پرداخت در جریان شروع نکنید.

## ۳. پشتیبان‌گیری و انتقال با دکمه

در همان مرورگر و همان دامنه سایت باز کنید:

```text
https://YOUR-SITE/storage-migration
```

لینک این صفحه در تنظیمات مدیریت هم اضافه شده است.

1. **«دانلود پشتیبان KV»** را بزنید؛ فایل `filmwork-kv-backup.json` را امن نگه دارید.
2. فایل پشتیبان ممکن است اطلاعات کاربران و Secrets ذخیره‌شده در تنظیمات قدیمی را داشته باشد؛ آن را در چت، GitHub یا فضای عمومی نفرستید. این خروجی آرشیو خام برای بازیابی توسط نگهدارنده است، نه دکمه بازیابی خودکار. Secrets و تنظیماتی که فقط در محیط Worker هستند جزو این فایل نیستند.
3. شرط پشتیبان‌گیری و توقف تغییرات را تأیید کنید.
4. **«شروع / ادامه انتقال»** را بزنید و صفحه را باز نگه دارید.
5. ابزار، حداکثر ۱۵ کلید در هر مرحله کپی می‌کند و سپس کلیدها را دوباره با KV مقایسه می‌کند. هیچ کلید KV حذف یا نوشته نمی‌شود.
6. اگر صفحه بسته شد یا شبکه قطع شد، دوباره همین دکمه را بزنید؛ cursor از آخرین مرحله ثبت‌شده ادامه پیدا می‌کند. داده و cursor هر مرحله با هم ثبت می‌شوند.
7. تنها وقتی پیام **«آماده فعال‌سازی»** را دیدید، مرحله بعد را انجام دهید.

صادرات مرورگری تا ۲۰ مگابایت محدود شده است؛ برای آرشیو بزرگ‌تر ابزار خروجی خارج از مرورگر لازم است. رکوردهای بیش از یک میلیون بایت در این مسیر مهاجرت/نوشتن پذیرفته نمی‌شوند؛ داده بدون اطلاع بریده نمی‌شود. یک سریال یا ایندکس بسیار بزرگ ممکن است به تفکیک ساختار در مرحله بعد نیاز داشته باشد.

**اگر مقدار داده‌ها متفاوت بود، ابزار D1 را آماده اعلام نمی‌کند.** علت تغییر KV یا دیتابیس اشتباه را بررسی کنید. داده را با حدس بازنویسی نکنید. برای شروع پاک از ابتدا از یک D1 خالی دیگر استفاده کنید؛ جدول‌های دیتابیس مورد استفاده را حذف نکنید.

## ۴. فعال‌سازی

پس از موفقیت و در حالی که هنوز حالت نگهداری روشن است، این دو مقدار را **با هم** تغییر داده و Deploy کنید:

```text
STORAGE_BACKEND = d1
STORAGE_MAINTENANCE = 0
```

اکنون مسیرهای عادی `Store` و هماهنگ‌کننده انتشار از D1 استفاده می‌کنند، نه KV. صف و نگاشت‌های جدید پشتیبان همچنان در EDITOR می‌مانند. نگاشت‌های قدیمی KV هم جزو رکوردهای منتقل‌شده‌اند و از مسیر سازگار D1 قابل خواندن هستند.

سایت در حالت d1 به KV fallback نمی‌کند؛ در صورت خطای DB، داده قدیمی یا حافظه موقت را به‌جای دیتابیس فعال استفاده نمی‌کند. اگر binding DB نباشد، جدول آماده نباشد یا مقدار STORAGE_BACKEND اشتباه باشد، خطای روشن داده می‌شود.

## ۵. بررسی واقعی پس از فعال‌سازی

پیش از بازگشت به فعالیت عادی:

- تعداد آثار و نسخه‌ها و چند قسمت سریال را بررسی کنید.
- با حساب موجود وارد شوید؛ موجودی کیف پول و سوابق پرداخت را مقایسه کنید.
- دریافت نسخه چندفایلی و زیرنویس همراه را تست کنید.
- دریافت از مخزن پشتیبان را با یک فایل آزمایشی بررسی کنید.
- یک فایل آزمایشی از ربات ثبت کنید و از نبود نسخه تکراری مطمئن شوید.
- Metrics دیتابیس D1 و KV را بررسی کنید. ابزار/Worker دیگری که همچنان KV را می‌نویسد با این تغییر متوقف نمی‌شود.

تا پایان تست هیچ دیتابیس قدیمی را حذف نکنید. اتصال‌ها و Secrets تلگرام و پرداخت همان قبلی‌اند. نشست‌ها و توکن‌های منقضی‌شونده با زمان انقضای مطلق منتقل می‌شوند؛ مهلتشان از نو شروع نمی‌شود.

## بازگشت و توقف

- **قبل از فعال‌کردن D1 و بدون تغییر جدید در آن:** می‌توانید `STORAGE_BACKEND=kv` و `STORAGE_MAINTENANCE=0` را Deploy کنید؛ KV اصلی دست‌نخورده است.
- اگر پس از توقف انتقال دوباره نوشتن KV را آزاد کردید، نسخه آماده/نیمه‌منتقل قبلی D1 را بدون انتقال و بررسی تازه فعال نکنید. در این نسخه، راه ساده و امن شروع مجدد، D1 خالی جدید است.
- **پس از نوشتن اطلاعات جدید در D1:** صرف تغییر متغیر به kv، داده‌ها را برنمی‌گرداند و اطلاعات جدید را از دسترس خارج می‌کند. ابتدا حالت نگهداری و پشتیبان/انتقال معکوس کنترل‌شده لازم است؛ ابزار بازگشت خودکار در این مرحله وجود ندارد.
- برای انتقال، KV باید قابل خواندن و list باشد؛ تمام‌شدن سهمیه write به‌تنهایی جلوی کپی را نمی‌گیرد، ولی محدودیت read/list می‌تواند انتقال را متوقف کند.

## نگهداری D1 و سقف رایگان

D1 هم سهمیه دارد. `ROWS WRITTEN` می‌تواند به‌علت ایندکس بیش از تعداد دستورات SQL باشد. این تغییر سقف روزانه KV را از مسیر نوشتن عادی سایت کنار می‌گذارد، ولی رایگان‌ماندن نامحدود یا حذف همه هزینه‌های CPU/DO را تضمین نمی‌کند.

رکوردهای منقضی در خواندن و فهرست‌گیری مخفی می‌شوند؛ پاک‌سازی فیزیکی خودکار در هر درخواست اجرا نمی‌شود تا write اضافی تولید نکند. نگهدارنده می‌تواند در زمان کم‌ترافیک و با پشتیبان، حذف منقضی‌ها را محدود انجام دهد:

```sql
DELETE FROM filmwork_records
WHERE key IN (
  SELECT key FROM filmwork_records
  WHERE expires_at IS NOT NULL AND expires_at <= unixepoch()
  ORDER BY expires_at LIMIT 500
);
```

آزمون محلی با SQLite واقعی و شبیه‌سازی API D1: `node tests/d1-storage.mjs` (Node 22.13+). آزمون محلی جایگزین تست نهایی روی حساب واقعی نیست.
