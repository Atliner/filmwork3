# اجرای سایت بدون KV — همهٔ داده‌ها روی D1

> نسخهٔ 3.61 دیگر برای کار کردن به KV نیاز ندارد. می‌توانی KV را کامل حذف کنی
> (یا هرگز نسازی) و همهٔ داده‌ها — تنظیمات، کاربران، کیف پول، آثار، شمارنده‌ها،
> rate-limit، توکن‌های پخش — روی **یک D1** بنشیند. سقف رایگان D1 برای همان حجمی که
> KV نمی‌کشید (۱۰۰٬۰۰۰ نوشتن در روز) کافی است.

## چرا این کار درست است؟

| سرویس (پلن رایگان) | خواندن/روز | نوشتن/روز | مشکل |
|---|---|---|---|
| KV | ۱۰۰٬۰۰۰ | **۱٬۰۰۰** | با ۲۰۰–۳۰۰ دانلود در روز تمام می‌شد |
| D1 | ۵٬۰۰۰٬۰۰۰ | **۱۰۰٬۰۰۰** | ۱۰۰ برابر جای نوشتن |

قبلاً KV فقط برای «داده‌های سبک» نگه داشته می‌شد؛ همان‌ها هم (تنظیمات، کش فهرست،
آرشیو پست‌ها) با هر بازدید یک خواندن KV می‌خواستند. حالا همه روی D1 است و KV لازم نیست.

## حالت‌های ذخیره‌سازی

| `STORAGE_BACKEND` | چه زمانی | مسیر داده‌ها |
|---|---|---|
| تنظیم نشده + فقط `DB` | **توصیه‌شدهٔ جدید** | همه‌چیز روی D1، اسکیما خودکار ساخته می‌شود |
| تنظیم نشده + `DB` و `KV` | نصب‌های قدیمی | `hybrid`: داده‌های پرتکرار D1، بقیه KV (رفتار قبلی) |
| `d1` | صریح | فقط D1 (حتی اگر KV بایند شده باشد) |
| `kv` | فقط برای انتقال قدیمی | فقط KV |
| `hybrid` | فقط اگر واقعاً KV می‌خواهی | D1 برای کلیدهای سنگین |

### راه‌اندازی نصب تازه (۵ دقیقه)

1. در Cloudflare → **Workers & Pages → D1** یک دیتابیس بساز (مثلاً `filmwork-main`).
2. در Worker → **Settings → Bindings** فقط یک چیز اضافه کن:
   - `D1 Database` با نام متغیر **`DB`** → همان دیتابیس.
3. هیچ KV نساز. متغیر `STORAGE_BACKEND` را هم نگذار (یا `d1` بگذار).
4. Deploy کن و سایت را باز کن. اولین درخواست خودش جدول‌ها را می‌سازد.
   در پنل ← تنظیمات ← «ذخیره‌سازی و فدراسیون D1» می‌بینی:
   `حالت: D1 تنها (بدون KV)` و `KV: لازم نیست (حذف شده)` و `ساخت خودکار اسکیما: ✓`.

> اگر با KV قدیمی کار می‌کردی و می‌خواهی داده‌ها به D1 بروند، از مسیر قبلی
> `/storage-migration` استفاده کن (KV لازم است) یا `D1_AUTO_BOOTSTRAP=1` بگذار و
> بدان که دادهٔ قدیمیِ KV منتقل نمی‌شود (نصب تازه).

### متغیرهای مربوط

| متغیر | پیش‌فرض | کار |
|---|---|---|
| `STORAGE_BACKEND` | خودکار | `d1` / `hybrid` / `kv` |
| `D1_AUTO_BOOTSTRAP` | `1` وقتی KV نیست | `1` = ساخت خودکار جدول‌ها و ثبت وضعیت ready؛ `0` = فقط از مسیر انتقال |
| `STORAGE_MAINTENANCE` | `0` | فقط هنگام انتقال دستی |
| `CACHE_KV` | — | هنوز **اختیاری** است؛ اگر بایند باشد فقط برای کش کوتاه استفاده می‌شود |

## D1 دوم برای محتوا (اکانت دیگر)

Cloudflare اجازه نمی‌دهد یک Worker به D1 اکانت دیگر **مستقیم** وصل شود؛ راه رسمی
«شارد» است و همین حالا در کد هست:

```
اکانت ۱ (سایت)                         اکانت ۲ (محتوا)
  DB: کاربران، کیف پول، تنظیمات          D1 خالی + Worker کوچک shard-proxy
  idx: فهرست آثار            ──HMAC──→  it:… / sub:…  (فقط آثار)
```

1. روی اکانت دوم (یا یک اکانت سوم) این را اجرا کن:
   ```bash
   node scripts/shard-installer.mjs
   ```
   خروجی: آدرس شارد + `SHARD_SECRET`.
2. در سایت: تنظیمات ← «ذخیره‌سازی و فدراسیون D1» ← آدرس و رمز ← «افزودن».
3. تمام. آثار جدید با hash کلید بین شاردها پخش می‌شوند و هر شارد سهمیهٔ رایگان خودش
   را دارد (۵ میلیون خوان / ۱۰۰ هزار نوشت روزانه).

> برای «همهٔ محتوا روی اکانت دوم و همهٔ داده‌های برنامه روی اکانت اول»: یک شارد کافی است؛
> `it:`، `sub:` و `src:` روی شارد می‌نشینند و کاربر/کیف پول/تنظیمات روی D1 اصلی می‌ماند.
> راهنمای کامل: `docs/D1-SHARDS.md`.

## پشتیبان‌گیری

- پنل ← ذخیره‌سازی: دکمهٔ پشتیبان D1 (JSON) — همان فرمت `/api/admin/storage/d1`.
- روی هاست اشتراکی: فایل `hosting/data/site.sqlite` را با `sqlite3 .backup` یا کپی
  هنگام توقف کوتاه بردار (WAL دارد).

## عیب‌یابی

| نشانه | معنی | راه‌حل |
|---|---|---|
| `انتقال D1 هنوز بررسی و نهایی نشده` | جدول‌ها نیستند و بوت‌استرپ خاموش است | `D1_AUTO_BOOTSTRAP=1` یا مسیر `/storage-migration` |
| `اتصال D1 با نام DB تنظیم نشده است` | Binding با نام `DB` نیست | Settings → Bindings → D1 → نام متغیر `DB` |
| `KV: ✗` در پنل | KV بایند نیست | در حالت D1 طبیعی است؛ نادیده بگیر |
| کندی نوشتن زیاد | هر درخواست زیاد می‌نویسد | `docs/ARCHITECTURE-FREE-TIER.md` بخش بودجه |
